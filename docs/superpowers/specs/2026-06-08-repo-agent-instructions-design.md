# Repo Agent Instructions Design

**Issue:** https://github.com/elasticclaw/elasticclaw/issues/140

## Goal

ElasticClaw should automatically surface repository-owned agent instruction files to OpenClaw whenever a claw works in a cloned repository. Users should not need to copy, relocate, or mention those files in workspace templates.

## Problem

Workspace templates can define their own `AGENTS.md`, and this repo already uses that for ElasticClaw/OpenClaw operating instructions. Many target repositories also define their own agent instructions, usually in `AGENTS.md` and sometimes in tool-specific files such as `CLAUDE.md` or `GEMINI.md`.

Today ElasticClaw injects template files and issue context before the agent starts, then clones configured GitHub repositories during provider bootstrap. If the agent starts in `~/.openclaw/workspace` rather than inside an individual repo, repository-local instructions can be easy to miss. The issue asks ElasticClaw to inject references to those repo files when they exist.

## Requirements

- Detect instruction files in each configured GitHub repository after the repository is cloned or updated.
- Surface references to detected files before the first useful agent turn.
- Preserve the workspace/template `AGENTS.md`; do not overwrite it with a repo `AGENTS.md`.
- Keep repository instruction files in their original repo locations.
- Support at least root-level `AGENTS.md`.
- Make the detector extensible for `CLAUDE.md`, `GEMINI.md`, and other well-known agent instruction files.
- Work consistently for Daytona, Replicated, and exe.dev bootstrap paths.
- Be idempotent across bootstrap retries, reconnects, checkpoint restore, and repo pull updates.
- Do not fail claw startup only because no repo instruction file exists.
- Do not send the initial wake or pipeline entry inject until repository instruction discovery has completed for managed provider bootstraps.

## Non-Goals

- No new UI or workspace configuration is required for the first implementation.
- No deep parsing or summarization of instruction files.
- No attempt to resolve conflicts between workspace instructions and repo instructions beyond making both visible.
- No recursive scan of every file in a large repository.
- No secret or token handling changes.

## Proposed Design

Add a small repository instruction discovery step that runs immediately after configured repositories are cloned or pulled. The step scans each repo root for known instruction filenames and writes a generated index file at the workspace root:

`~/.openclaw/workspace/REPO_INSTRUCTIONS.md`

The generated file should contain only references and brief guidance, not copied instruction bodies. Example content:

```markdown
# Repository Instructions

ElasticClaw detected repository-owned agent instruction files. Read the relevant files before making changes in that repository.

## elasticclaw

- `elasticclaw/AGENTS.md`
- `elasticclaw/CLAUDE.md`
```

The workspace/template `AGENTS.md` should also mention this generated file. Since templates are user-owned and may omit that text, ElasticClaw should inject a small deterministic section into the existing workspace `AGENTS.md` at bootstrap time when repositories are configured:

```markdown
## Repository Instructions

If `REPO_INSTRUCTIONS.md` exists, read it before working inside any cloned repository. It lists repository-owned instruction files such as `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md`.
```

If no workspace `AGENTS.md` exists, ElasticClaw should create one containing only this section. If the section already exists, do not duplicate it.

This keeps workspace-level behavior and repo-level behavior distinct:

- `AGENTS.md` at workspace root remains ElasticClaw/OpenClaw operating guidance.
- `REPO_INSTRUCTIONS.md` is generated by ElasticClaw and points to repo-owned instruction files.
- Repo instruction files remain inside their repo directories and keep their native scope.

## Instruction File Matching

Start with this ordered list:

- `AGENTS.md`
- `CLAUDE.md`
- `GEMINI.md`

Match only root-level files in each cloned repo for the first implementation. The helper should be written so additional names can be added later without changing call sites.

Case sensitivity should follow the remote filesystem behavior. Do not treat `agents.md` as equivalent to `AGENTS.md` in the first pass because OpenClaw/Codex-style conventions usually use exact uppercase names and Linux providers are case-sensitive.

## Data Flow

1. Resolve configured repositories from `github_repos` as today.
2. Clone or pull each repository into `~/.openclaw/workspace/<repo-name>`.
3. Run repo instruction discovery over the cloned repo directories.
4. Write or remove `REPO_INSTRUCTIONS.md`:
   - write it when at least one instruction file is found;
   - remove the generated file when no instruction files are found, if it previously existed.
5. Ensure workspace `AGENTS.md` contains a single “Repository Instructions” reference section.
6. Continue existing workspace readiness verification.
7. Mark `bootstrap_ok=1` only after repository sync, instruction discovery, template file writes, checkpoint restore, and readiness verification have completed.
8. Allow the initial wake or pipeline entry inject only after `bootstrap_ok=1`.

Daytona already uses `bootstrap_ok` to prevent early wake. Replicated and exe.dev should use the same gate as part of this change. If their bridge connects while bootstrap is still finishing, registration should remain in `starting` and should not send the wake message until a later heartbeat observes `bootstrap_ok=1`.

## Provider Integration

### Daytona

The best hook is in `bootstrapDaytona` after clone/pull succeeds and before final workspace readiness and `startDaytonaBridge`.

Expected file area:

- `pkg/hub/server.go`
  - after the `clone repos done` block
  - before the final repository readiness gate

### Replicated

The current Replicated path writes template files, restores checkpoints, installs the GitHub credential helper, and then clones repos inside `buildGitHubCredentialHelper`. To avoid putting more complex generated-file logic into a long shell string, split repo sync and instruction discovery into testable helpers.

Because the Replicated bootstrap script starts `claw-bridge` before the hub finishes post-bootstrap file and repo setup, this implementation must also extend the `bootstrap_ok` gate beyond Daytona. Replicated should set `bootstrap_ok=1` only after template files, checkpoint restore, GitHub credential setup, repo sync, and repo instruction discovery succeed. Before that point, a connected bridge must remain unwoken.

Expected file area:

- `pkg/hub/server.go`
  - `bootstrapReplicated`
  - `buildGitHubCredentialHelper`
- `pkg/hub/bootstrap.go`
  - pure shell-generation helpers if script generation remains the preferred pattern

The spec allows either:

- keep clone/pull in `buildGitHubCredentialHelper` and append a generated shell snippet for instruction discovery, or
- extract a new `buildGitHubRepoSyncScript` that includes clone/pull plus instruction discovery.

The second option is preferred because the existing helper name is already broader than credentials.

### exe.dev

The exe.dev path uses `GenerateReplicatedBootstrapScript`, then writes template files from the hub. It should use the same repo sync and instruction discovery script as Replicated, or the same Go-side helper adapted to `p.Exec`.

exe.dev should follow the same `bootstrap_ok` behavior as Replicated. If the bridge connects before the hub finishes repo sync and instruction discovery, it must not receive wake or pipeline task injection until the provider bootstrap sets `bootstrap_ok=1`.

Expected file area:

- `pkg/hub/server.go`
  - `bootstrapExedev`
  - the point after template files are written and before bootstrap completion

## Implementation Shape

Create a testable helper that describes repo instruction discovery without reaching into provider details:

```go
var repoInstructionFileNames = []string{"AGENTS.md", "CLAUDE.md", "GEMINI.md"}

func buildRepoInstructionsIndex(repoDirs []string, existingFiles map[string][]string) string
```

For shell execution paths, create a generated script helper:

```go
func buildRepoInstructionDiscoveryScript(workspaceDir string, repos []types.GitHubRepoAccess) string
```

The shell helper should:

- `cd` to the workspace directory;
- derive repo directory names with the existing `repoDirectoryName`;
- test each known filename with `[ -f "$repo/$name" ]`;
- write a temporary file then atomically move it into `REPO_INSTRUCTIONS.md`;
- remove `REPO_INSTRUCTIONS.md` if no instruction files exist;
- append the workspace `AGENTS.md` reference section only if absent.

Use the existing `shellQuote`, `repoDirectoryName`, and sanitization helpers rather than introducing ad hoc quoting.

## Error Handling

- Missing repo directory: return an error only if the existing readiness gate would also treat the repo as required.
- No instruction files: success, no generated index.
- Failure writing `REPO_INSTRUCTIONS.md` or updating `AGENTS.md`: fail bootstrap, because the feature is specifically about making instructions visible before the agent starts.
- Invalid repo path/name: reuse existing repo validation and directory-name logic.
- Bootstrap retry: generated output must be deterministic and overwrite the previous generated file.
- If repo instruction discovery fails after a bridge has already connected, keep the claw in `starting` or move it to `error`; do not send the task wake with incomplete instruction context.

## Testing

Add focused unit tests around the new helpers.

Suggested tests:

- `TestRepoInstructionFileNamesIncludesAgents`
  - verifies `AGENTS.md` is in the supported list.
- `TestBuildRepoInstructionDiscoveryScriptReferencesKnownFiles`
  - verifies the script checks `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md`.
- `TestBuildRepoInstructionDiscoveryScriptWritesIndexAtomically`
  - verifies the script writes a temp file and moves it into `REPO_INSTRUCTIONS.md`.
- `TestBuildRepoInstructionDiscoveryScriptDoesNotDuplicateAgentsSection`
  - verifies the generated script guards the `AGENTS.md` injected section.
- `TestDaytonaBootstrapRunsRepoInstructionDiscoveryBeforeBridgeStart`
  - verifies discovery appears before `startDaytonaBridge` in the Daytona flow, either through helper-level ordering or a command-building unit test.
- Extend the existing credential helper test to verify Replicated repo sync includes discovery after clone/pull.
- Add or extend a websocket/bootstrap test to verify non-Daytona providers do not send wake or pipeline entry inject while `bootstrap_ok=0`.
- Add a provider bootstrap test or helper test verifying Replicated and exe.dev set `bootstrap_ok=1` only after repo instruction discovery succeeds.

Run:

```bash
go test ./pkg/hub -run 'RepoInstruction|GitHubCredential|DaytonaBootstrap'
go test ./pkg/hub
```

For final validation, run:

```bash
go test ./...
```

## Documentation

This changes user-facing workspace behavior, so documentation should be updated in `elasticclaw/elasticclaw.ai`.

Docs should explain:

- workspace templates can define ElasticClaw/OpenClaw operating instructions;
- cloned repos can define their own repo instructions;
- ElasticClaw generates `REPO_INSTRUCTIONS.md` automatically when such files exist;
- users do not need to copy repo `AGENTS.md` into workspace templates.

## Open Questions

- Whether `CLAUDE.md` and `GEMINI.md` should ship in the first implementation or wait until a later issue.
- Whether nested `AGENTS.md` files should be indexed. This spec intentionally starts with root-level files only.
- Whether the generated index should be named `REPO_INSTRUCTIONS.md` or placed under `.elasticclaw/`. The root-level file is recommended because agents already operate from the workspace root and visible Markdown files are easy to discover.

## Acceptance Criteria

- A claw with a repo containing `AGENTS.md` starts with `REPO_INSTRUCTIONS.md` at the workspace root.
- The generated index lists the repo-relative path to that `AGENTS.md`.
- Workspace `AGENTS.md` contains exactly one reference section telling the agent to read `REPO_INSTRUCTIONS.md` when present.
- A repo without instruction files starts successfully and does not create stale instruction references.
- Daytona, Replicated, and exe.dev flows either share the same discovery helper or have tests proving equivalent behavior.
- Daytona, Replicated, and exe.dev do not send initial wake or pipeline entry inject before `bootstrap_ok=1`.
- Existing template file injection and flake staging behavior remain unchanged.
